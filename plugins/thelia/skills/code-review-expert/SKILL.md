# Code Review Expert - Standards for Thelia 3

This skill guides PHP/Symfony code reviews for Thelia 3 projects. It defines the methodology, severity levels, and review rules organized by category.

## Philosophy

- **Progress over perfection**: approve once the code improves overall health, even if imperfect.
- **Focus on correctness**: bugs, security, data integrity. Not formatting (automated tools handle that).
- **One lead reviewer** per PR. Others comment, but the lead decides.
- **PR size**: flag any PR over 400 lines and ask for a split.

## Severity System

| Marker | Level | Meaning | Gate |
|--------|-------|---------|------|
| ❌ **Blocking** | Critical/High | Production bug, security flaw, data loss | Merge blocked |
| ⚠️ **Important** | Medium | Logic error, edge case, perf issue, missing test | Non-blocking, strongly recommended |
| 💡 **Suggestion** | Nit | Style, naming, optional refactoring | Non-blocking, optional |
| ✅ **Positive** | Praise | What was done well | At least 1 per review |
| 🟣 **Pre-existing** | Pre-existing | Existing bug, not introduced by this PR | Non-blocking, separate ticket |

### Decision Rule

- **Blocking**: a user could be impacted in production.
- **Important**: a developer will struggle to maintain this code, but users are safe.
- **Suggestion**: comfort improvement, no functional impact.

## Output Format

Each finding follows this format:

```
{marker} [{file}:{line}] {Short title}

**Problem**: {concise description}
**Suggestion**:
```php
// corrected code
```
```

## Exclusions: do not review

- `migrations/` (auto-generated by Doctrine; reviewing the SQL is fine, rewriting is not)
- `vendor/`, `node_modules/`
- `*.lock` files
- Test fixtures (data, not logic)
- Generated code under `src/Generated/` or equivalent

## Review Categories

Detailed rules are in the `references/` files. Summary by category:

### Security (always blocking)

See `references/security-checklist.md` for the full list.

- SQL injection (string concatenation in Doctrine/DBAL queries)
- XSS (`|raw` in Twig on user-controlled data)
- Missing CSRF on action forms
- Hardcoded credentials
- `unserialize()` / `eval()` / `exec()` in application code
- Voter without subject (IDOR)
- Missing rate limiting on sensitive endpoints
- Missing serialization groups on API Platform (exposing internal data)
- File uploads validated by extension instead of content (`finfo`)
- Logging PII, passwords, or tokens
- Error messages exposing internals (`$e->getMessage()` in responses)

### PHP / Correctness (blocking or important)

See `references/php-review-rules.md` for the full list.

- Missing `declare(strict_types=1)`
- Missing `final readonly` on services/DTOs
- Missing guard clauses (nesting over 2 levels)
- Catch-all `catch (\Exception)` or `catch (\Throwable)`
- `json_decode()` without `JSON_THROW_ON_ERROR`
- `mixed` accepted/returned without narrowing
- Business logic in controller or command

### Symfony / Architecture (blocking or important)

See `references/symfony-review-rules.md` for the full list.

- `ContainerInterface` injected into a service
- Events dispatched inside a transaction (nested flush)
- Messenger: entity as message parameter instead of an ID
- Messenger: non-idempotent handler
- Doctrine: `flush()` inside a loop
- Doctrine: missing `onDelete` on JoinColumn
- Doctrine: incomplete multi-level cascade
- Migrations: NOT NULL without DEFAULT, destructive drop, migration edited post-deploy
- API Platform: operations without `security`

### API Consumers (blocking)

A common anti-pattern: a third-party API responds with **HTTP 200 and a body like `{"status":"failure",...}`** on business error (instead of raising an exception or returning 4xx/5xx). Consumer code that only checks the HTTP status code silently swallows the failure, with no retry and desynchronized data.

Flag:
- `try/catch` on an HTTP call followed by `return $response;` without inspecting the body
- Code that treats HTTP 200 as success without checking `$body['status']` / `$body['success']` / `$body['error']`
- Missing email/notification on business refusal (the `catch \Exception` fires an alert, but `status:failure` does not)

Require: explicit body check, mapping to an enum or business exception, and symmetric alerting between network exceptions and business refusals.

### Performance (important)

See `references/performance-checklist.md` for the full list.

- N+1 queries (`findAll()` followed by relation access in a loop or Twig)
- Inverse `OneToOne` (forces an eager load in Doctrine)
- `find()` just to set a FK (use `getReference()` instead)
- Missing index on JoinColumn or filtered column
- `count($collection)` instead of `isEmpty()`

## REVIEW.md

Each project can have a `REVIEW.md` at its root for project-specific review rules. This file is read during reviews only, not during development. See `assets/REVIEW.md.template` for the template.
